# AR Lab project: Event badge AR

## Goal
Point an iPhone at an event ID badge and have media appear locked onto it. Phase 1 is a photo, phase 2 is a video with sound.

## Platform and versions
- Web app in iPhone Safari, with no app install.
- MindAR image tracking 1.2.5 (mindar-image-aframe) plus A-Frame 1.5.0, loaded from a CDN with pinned versions.
- Exact URLs (jsDelivr): https://cdn.jsdelivr.net/npm/aframe@1.5.0/dist/aframe-v1.5.0.min.js (bundles three.js r158) and https://cdn.jsdelivr.net/npm/mind-ar@1.2.5/dist/mindar-image-aframe.prod.js. A-Frame 1.5.0 is the version the MindAR 1.2.5 docs pair it with, so no downgrade needed.
- A-Frame 1.5.0 gotcha: the VR button component is `xr-mode-ui` (older MindAR examples say `vr-mode-ui`, which does nothing in 1.5.0). Color is handled by `renderer="colorManagement: true"` (the `color-space` attribute in old examples doesn't exist in 1.5.0).
- Hosting: GitHub Pages at https://jigarkpat3.github.io/ar-badge/ (see Hosting). Add ?debug to the address for the on-screen debug panel.

- 2026-11-23 (after Jigar's first iPhone test): Fit. The side overhang is not a size error. Checked: badge.jpg has no margin (its edges are the badge; at most a 3-4 px light rim on the right, under 0.5%), its 3:4 shape matches the measured 1.335. MindAR 1.2.5's aframe.js sizes the camera video with "cover" scaling and derives the 3D camera from the same numbers, so the overlay matches the badge to 0.3% in headless tests with portrait 480x640, landscape 640x480 and 720x1280 cameras on phone-sized screens. Causes of what he saw: (1) lag from the old filter (filterBeta 0.001 smoothed everything at ~1 Hz), so with side-to-side hand motion the photo trailed the badge and stuck out on one side, then the other; his recording shows the badge peeking out beside the photo; (2) the photo had square corners and the badge has rounded ones (about 24 px of 750), so the photo's corners stuck out past the badge. Fix: new smoothing (below) and rounded corners. No recompile. Unverified on iPhone: if the camera changes frame size after start, MindAR keeps the old size. The ?debug panel shows "camera" vs "input" sizes so we can check.
- 2026-11-23: Smoothing. MindAR's One Euro filter runs on the 16 raw matrix numbers with one beta for both rotation (values ~0-1) and position (values in hundreds), so no single beta suits both. Chosen: filterMinCF 0.001 (1 Hz at rest) and filterBeta 10 (rotation stays steady when still and catches up when tilting; position passes through mostly unfiltered). Our own follow-badge component (js/components.js) then smooths position/rotation/size each rendered frame with frame-rate-independent exponential smoothing that adapts to motion: 0.12 s smoothing time when still (difference under 0.6% of badge width / 0.34 deg), down to 0.01 s when moving (over 2.5%). Depth counts 0.3x when measuring motion because it's the noisiest. Offline simulation with MindAR's real filter code (30 fps tracking, assumed noise of ~1 px, depth 0.75%, 0.5 deg): still jitter 0.38 px/frame (old 0.44, MindAR default 3.13); error while sliding 1 badge width/s 6.1 px (old 18.7, unfiltered 6.0); while tilting 40 deg/s 3.9 px (old 14.0, unfiltered 3.4). warmupTolerance/missTolerance (both exist in 1.2.5, default 5 frames) left at 5. All values are in TUNING at the top of js/app.js.
- 2026-11-23: Dropouts and fades. follow-badge keeps the last pose for 500 ms after MindAR's targetLost, then fades out over 250 ms; fades in over 200 ms on found. If the badge comes back while it's being held, the photo glides from where it was instead of popping.
- 2026-11-23: Rounded corners come from an alpha map (a small canvas drawn at startup: white rounded rectangle on black), radius 0.032 of the badge width. The same thing will work on the video later. overlay.jpg stays a 136 KB JPG (a PNG with baked corners was 1.04 MB).
- 2026-11-23: Startup. Cause of the small box: MindAR adds its camera <video> to the page as soon as start() runs, with no size, so it shows at the default 300x150 in the top-left until its resize code runs after the camera and TensorFlow are ready; the page behind was white. Fix: a dark "Starting camera…" cover from the tap until arReady, then a forced resize and two frames' wait before lifting it. A video "resize" listener re-fits the view if the camera changes size. Note: don't put a background on <body>; it paints over MindAR's video (z-index -2).
- 2026-11-23 (round 3, after Jigar's second iPhone test): Skew cause. MindAR 1.2.5 hard-codes a 45 deg vertical field of view for the camera (controller.js: fovy = 45, f = inputHeight/2 / tan(22.5 deg)) and uses it both to work out the badge's 3D pose and to draw it. A phone camera sees much wider. Measured from Jigar's recording (SIFT matching of badge.jpg + the focal length from each tilted view's homography): about 71 deg along the long side, which fits a 24 mm-equivalent iPhone main camera. With the wrong focal length the best 3D pose can't reproduce a tilted card's perspective, so the photo looks skewed when the badge is tilted and fine when it's flat. Headless test with badges rendered by a 65-71 deg camera: corner error was 6-16% of the badge width at 25-40 deg tilts with MindAR's 45 deg; with the real FOV it's 0.7-1.2%. A 5 deg FOV error still gives 2-3%. Not the cause: the 488 vs 480 size (his panel actually showed input 480x640 = camera 480x640), the follow-badge smoothing (it moves a rigid pose; scale is now forced uniform anyway), or a photo offset.
- 2026-11-23: FOV fix. js/camera.js wraps MindAR's own _resize(), which runs right after MindAR creates its controller and before it loads targets.mind. There it rebuilds controller.projectionTransform and projectionMatrix (with MindAR's own _glProjectionMatrix) from TUNING.camera.fovDeg (default 70, along the long side). Same fields and layout as the 1.2.5 source, so the tracker, the worker and the A-Frame camera all use the real numbers. Add ?fov=NN to the address to try other values without editing code.
- 2026-11-23: Camera resolution. The 1.2.5 source asks getUserMedia for {audio:false, video:{facingMode:'environment'}} only, so iOS gives 480x640. camera.js wraps navigator.mediaDevices.getUserMedia to add width ideal 1280, height ideal 720. Landscape numbers on purpose: browsers apply size constraints to the landscape sensor and rotate (a portrait camera gets 720x1280); asking for portrait numbers on iOS can return an unrotated landscape preset. "ideal" never fails; the debug panel shows asked vs got. Chosen 1280x720 over 1920x1080: MindAR processes every frame at full camera resolution, so cost scales with pixels (720p = 3x the pixels of 480x640, 1080p = 6.75x). Headless (software GPU) cost: tracking updates 55/s -> 35/s at 720p -> 21/s at 1080p; time to detect 158 -> 213 -> 366 ms. On the iPhone expect somewhat lower tracking rate, more heat and battery than before, but a sharper picture that's also less zoomed in (720x1280 nearly matches the 430x775 screen shape, so less is cropped off the sides).
- 2026-11-23: Frame-size safety. camera.js waits until the stream reports the same size for 3 frames before handing it to MindAR (MindAR reads the size once). If the camera's size still differs from MindAR's input size at arReady or later, app.js restarts AR (stop + start, at most twice) under the dark cover. Tested with a fake camera that switches from 640x480 to 480x640 after start: before, the badge was never found; now it restarts once and fits to 0.3%.
- 2026-11-23: Hint. It was driven by MindAR's raw targetLost, so it appeared while the photo was still held or fading. The 'tracking' Jigar saw at 00:21 was the debug panel lagging: it refreshed once a second, and the lost event (tracking dipped during fast motion) came after the last refresh. Now follow-badge emits 'overlaystate' and the hint shows only when the state is 'hidden'. The panel refreshes 4 times a second over a rolling 1-second window. Headless: 0 frames with the hint showing while the photo was visible.

- 2026-11-24 (round 4, after Jigar's third iPhone test, test3-recording.mp4): Camera size. The panel was right: "got" is the video's real decoded size (videoWidth x videoHeight) and read 480x640, so the 1280x720 request did not take effect. The round 3 note above about landscape numbers is wrong for this iPhone: the request reached Safari, but Safari compared our numbers with its sizes turned upright, and by the browser's "closest match" rule 480x640 is closer to 1280x720 than 720x1280 is. Different iOS versions compare differently, so camera.js now asks with the numbers the way the screen is held (720x1280 when upright), checks the real size, and if it's still small asks again (applyConstraints) with the numbers swapped. Each step is kept only if the frame didn't get smaller, and a refused request changes nothing. Tested with fake cameras that compare both ways, refuse applyConstraints, or only have 640x480: always ends at the best size available. "Quality looks better" in round 3 came from the skew fix (the photo sits flat on the tilted card), not from more pixels; his test2 and test3 frames are both 480x640.
- 2026-11-24: Frame rate. camera.js also asks for 60 frames/s (TUNING.camera.fps) after the size is settled, and keeps it only if the size didn't drop. iPhones default to 30. MindAR already runs about 60 times a second, so at 30 it analyses each frame twice; at 60 each frame is fresh. The panel shows the result ("@NNfps").
- 2026-11-24: Lag budget. Measured from test3-recording (SIFT track of the photo vs optical flow of the hand around it, cross-correlated): the photo trails the hand by about 100 ms (best match 83-117 ms). At his typical fast moves (1.4 badge widths/s, 90th percentile) that's 14% of the badge width, matching what the reviewer saw (10-20%, more on fast tilts). The parts: (a) follow-badge smoothing and (b) MindAR's One Euro filter add only about 1-3% of the badge width, roughly 5-15 ms (offline simulation with MindAR's real filter code, analysis/ + pwtest/sim2.mjs). (c) The pipeline: MindAR's <video> shows the newest camera frame, but the pose comes from the frame MindAR loaded earlier and has just finished analysing. That is about 85-100 ms on the iPhone and 33-83 ms headless. So (c) is almost all of it.
- 2026-11-24: Lag fix (js/sync.js). Show the frame the pose came from. MindAR 1.2.5 copies each frame it analyses into controller.inputLoader.context.canvas (input-loader.js), and its processing loop (controller.js processVideo) reports "processDone" right after the pose for that frame. sync.js wraps the controller's onUpdate (hooked in _resize, like the FOV fix). On processDone it copies that canvas onto our own canvas, which sits exactly over MindAR's video (same CSS, z-index -1), so the picture and the photo update together. It runs only while the photo is on screen; while searching, the live video shows, because searching is slower than tracking. It skips frames where tracking failed, because MindAR keeps the last good pose for those, so we keep the last good picture too. If MindAR's frame is rotated relative to the video, we fall back to live. Cost: one canvas copy per analysed frame. Trade-off: the whole camera view is now about 0.1 s behind reality, the way ARKit apps work. Switch it off with ?sync=0. Headless moving-badge test (lagtest.mjs, fake camera with a frame-number barcode, trail = worst corner gap vs the badge in the picture on screen, % of badge width, median / 95th percentile): slow sway (peak 1.9 widths/s) v3 3.1-5.9 / 14-23, v4 1.0-1.3 / 2.7-4.5; fast sway (peak 3.8 widths/s) v3 22-23 / 42-46, v4 1.2-1.3 / 3.9-6.8; 720x1280 camera, fast: v3 33 / 67, v4 1.3 / 3.4. Rare multi-frame jumps happen when MindAR itself loses the pose under very fast motion (with sync on or off, and in v3).
- 2026-11-24: Retune now that the pipeline lag is gone. MindAR filterBeta 10 -> 30 (minCF stays 0.001). follow-badge: restSmoothTime 0.12 -> 0.22, fastSmoothTime 0.01 -> 0 (no delay when moving), restMotion 0.006 -> 0.008, fastMotion 0.025. Grid search in the simulation, keeping rest jitter at or below v3: rest jitter 0.10 -> 0.064% of width per frame (35% less), smoothing trail on fast slides 3.2 -> 1.3% and wobbles 2.7 -> 1.8%. Real-camera noise can't be reproduced headless (a still synthetic badge gives zero jitter), so the rest-jitter gain needs checking on the phone.

- 2026-11-24 (round 5, approved by Jigar after "it's much better"): Framing screen between the camera starting and the photo. Flow: tap 1 starts the camera; a see-through framing screen shows a badge-shaped 3:4 outline (about 74% of the screen width, the rest dimmed) and tips (hold the badge flat, fill the outline, good light, avoid glare). MindAR tracks in the background, and the outline turns green on targetFound. "Start the experience" unlocks after TUNING.framing.steadyMs (1500 ms) of unbroken tracking. targetLost before then (or while waiting to be tapped) locks it again and restarts the wait. Tap 2 fades the photo in. Why: the first overlay frame used to appear before the filters had settled, so it could swing in skewed, and people didn't know how to hold the badge. During framing, follow-badge keeps following the badge with its photo invisible (new `revealed` flag), so when the button unlocks the smoothing has settled and the photo fades in already in place. Tap 2's handler is synchronous with a marked spot for video.play(), so the video can play with sound on iOS. After tap 2, losing the badge keeps the hold, fade and hint behaviour and never returns to framing. The hint shows only in the experience. Frame-sync canvas: off during framing (live view), on only while the photo is visible. With no photo to line up, the live view is the newest frame and the smoothest, so framing feels responsive. ?debug adds "phase framing steady N/1500 ms" or "phase experience"; ?sync=0 still works. Safe areas: max(..., env(safe-area-inset-*)) padding; the button is at least 56 px tall. Headless (controllable fake camera): searching, found+locked, lost before unlock re-locks, unlocked exactly 1500 ms after found, photo stays at opacity 0 the whole time before the tap, fades in after it, hold -> fade -> hint on loss without the framing screen, back on re-find, no console errors.

- 2026-11-24 (feature 6, Jigar: "let's try a video now, with audio"): Video encode. Jigar's video (reference/overlay-source.mp4, 1080x1920 9:16, 50 fps, 58.7 s, 31.6 MB; not committed) is center-cropped in the encode to 1080x1440 (3:4), so the file itself is 3:4 like the badge and fills it with no stretching. The top and bottom 240 px of the original are cut (12.5% each, 25% of the height in total). Result: assets/overlay.mp4 is 14.2 MB, 1.94 Mbps total. Poster: assets/overlay-poster.jpg, the first frame (52 KB).
- 2026-11-24: Video on the badge. The plane's material starts with the poster and switches to the <video> on its first "playing" event. So the badge never shows a black or empty frame, and the poster matches the first frame. A-Frame 1.5.0 turns a <video> src into a THREE.VideoTexture and, with renderer colorManagement on, sets it to sRGB (material utils setMap -> renderer applyColorCorrection; checked in headless: colorSpace "srgb"). Rounded corners: the alpha map is re-applied on materialtextureloaded. The <video> sits in <body>, not <a-assets>: A-Frame's asset loader makes the whole scene wait until a preload="auto" or autoplay media asset is fully buffered (mediaElementLoaded), which would hold the start button on a 14 MB download. It's kept in the page at 2x2 px with opacity 0, not display:none (some phones stop decoding hidden videos). Attributes: playsinline, webkit-playsinline, preload="auto", loop, no autoplay (A-Frame's fixVideoAttributes adds crossorigin="anonymous"; same origin, so fine).
- 2026-11-24: Sound and play/pause (js/video.js). Tap 1 calls video.load() so iOS starts downloading during framing. "Start the experience" calls video.muted = false; video.play() first thing, synchronously. WebKit's iOS policy allows sound only from play() inside a tap. Once an element has been played from a tap, later play()/pause() on it need no new tap; we rely on that for resume-on-found. If play() is refused, it falls back to muted play (always allowed inline) plus a "Tap for sound" button. Pause when the photo has fully faded (state 'hidden'). Resume on 'tracking'. If it was gone longer than TUNING.video.restartAfterMs (5000 ms, Jigar's choice) it starts over from 0, otherwise it carries on where it paused. Mute toggle bottom-right (52 px, safe-area aware). Returning to the tab resumes if the photo is showing. ?debug shows video time/duration, playing/paused, muted/sound, readyState and size. Headless (real click gestures, default Chrome autoplay policy): plays with sound, frame-sync on, paused after fade, resumed from 3.9 s after a 2 s loss, restarted from 0 after a 6 s loss, mute toggle works. A forced refusal shows "Tap for sound", which turns the sound on. ?sync=0 and the no-gesture policy also pass. assets/overlay.jpg is no longer used (kept for reference).

- 2026-11-24 (video round 2, Jigar: "It's so good", but a little jitter at the edges and he didn't like the emoji button): Edge causes, checked in the A-Frame 1.5.0 source and test6-recording.mp4. (1) A-Frame turns antialiasing off on phones (renderer setupRenderer: antialias: !isMobile), so the plane's hard border is drawn as pixel stairs. (2) A-Frame caps its canvas at 1920 px (maxCanvasWidth/Height defaults), so on Jigar's 430x775 @3x screen the 3D layer rendered at 1065x1920 and was stretched 1.21x: stairs of about 1.2 screen px, and a softer video. (3) The old alpha map was hard up to the plane border, so the visible edge was the aliased border itself. (4) The real badge peeked out by about 1% (light rim at the corners). Every sub-pixel move flips the stairs, which is what read as "edge jitter". Measured rest motion in the recording, held still (3.0-5.5 s, sub-pixel edge tracking against optical flow of the hand): about 0.8 screen px RMS (0.1% of the badge width), 3-5 px peak-to-peak, 0.35-0.5 px per frame. Small, but enough to make the stairs crawl.
- 2026-11-24: Edge fixes. renderer maxCanvasWidth/Height -1, so the 3D layer renders at full screen resolution (1290x2325); one textured quad, cheap. The alpha map is now 1024x1365, computed from the exact rounded-rectangle distance, with a smoothstep fade over TUNING.overlay.edgeSoftness (0.004 of the width, about 3 screen px) that reaches 0 at the plane border. The GPU blends the edge smoothly (linear + mipmaps), so no MSAA is needed and antialias stays off (saves GPU for tracking). Overscan: TUNING.overlay.overscan 1.04 makes the plane 4% bigger than the badge (2% each side) so the real edge never shows. That's a little more than 3% because the calmer rest smoothing can sit about 1% off on slow drifts. The corner radius grows with it (badge radius + margin) so the corner stays concentric with the badge. Headless iPhone-like render (DPR 3, mobile UA): before = 1065x1920 canvas, stair-stepped edges and the badge rim showing at the corner; after = 1290x2325, smooth edges, no rim (reference/test7-edges-before-after.png).
- 2026-11-24: Rest smoothing: restSmoothTime 0.22 -> 0.4 s, restMotion 0.008 -> 0.012 (filterMinCF 0.001 / beta 30 and fastSmoothTime 0 unchanged, frame-sync unchanged). Simulation: rest jitter 0.064 -> 0.033% of the width per frame (about half), trail on slides, shakes and tilts unchanged; slow creep (0.2 widths/s) 1.37 -> 1.58%, hidden by the overscan. Headless moving-badge test with sync: median trail 1.3-1.4% vs 1.2% before (same within noise).

- 2026-11-24 (round 8, Jigar: "It was wobbly the first time I tried, then when I tried to screen record it stopped"): First-launch wobble. No recording of the wobbly run, so the cause isn't proven. What differs on a first run, from the code: (1) the browser has to compile MindAR's GPU programs (tfjs WebGL kernels) the first time detection and tracking run; later runs reuse the cache. Headless, every first find shows a ~1.15 s frozen frame and 14-20 tracking updates/s for the first second, then 55-60/s (cold.mjs, CPU x4); (2) iOS autofocus/exposure settling right after the camera opens; (3) the 14 MB video download starting in tap 1 alongside startup; (4) a camera restart if the frame size changes. Headless cold vs warm (CPU x4, 8 Mbps) showed no other difference. Best suspect: (1)+(2), the first seconds of tracking are slow and noisy, and the old unlock (1.5 s of unbroken tracking) could open while it was still settling. Fix: the unlock now needs 1.5 s of tracking that is also healthy, at least TUNING.framing.minTrackRate (25) updates/s and the badge calm (speed < maxSpeed 0.6), checked every 100 ms; a slow start just makes the wait longer.
- 2026-11-24: Run log (js/runlog.js). - 2026-11-24: Soft shadow (soft-shadow component in components.js). Jigar's table screenshot looked pasted on because the 4% overscan covers the badge's real shadow. - 2026-11-24 (Jigar: "add on screen tips about framing, lighting, staying still..."): Live tips (js/coach.js). One message at a time, in the existing pills: the framing status pill while framing, the bottom glass hint pill during the experience (it replaces the old hint logic, so never two pills). Measured cheaply: tracking rate (targetUpdate/s), badge speed (pose vs ~0.25 s ago, peak-hold easing down over 0.5 s, so tracking jitter isn't counted), size and cut-off from the projected corners, angle between badge normal and camera, and every 500 ms a 32x32 brightness sample of the camera and a 32x40 sample of the badge area for the biggest blown-out (all channels >= 250) patch. Each problem has on/off thresholds (hysteresis); a tip must be wanted 0.5 s (framing) / 1 s (experience) to show, stays at least 1.5 s, clears after 0.6 s. All in TUNING.coach. ?debug shows the tip and metrics. Headless (tips.mjs, wooden-table fake camera): every tip triggered in its case and the clean badge gave glare 0% and no tip. Screenshots in reference/test8/.
- 2026-11-24 (round 9, Jigar: "do github repo, I don't see a downside besides it being slow"): Media manager, with the repo itself as storage. Static admin page at /admin/ (admin/index.html, github.js, prepare.js, admin.js, admin.css), linked by a small "Admin" link on the start screen and on the desktop notice. Login = a fine-grained GitHub token (only jigarkpat3/ar-badge, Contents read and write). - 2026-11-24: media/manifest.json is the library: {version, rev, updatedAt, live, items: [{id, type video|image, file, poster, title, uploadedAt, w, h, sizeBytes, duration?, focus?}]}. Migrated: the SĀCHU video (assets/overlay.mp4, live) and the first photo (assets/overlay.jpg). Their files stay in assets/ and are never deleted by the admin page (only media/ files are), because the badge page falls back to assets/overlay.mp4 if the manifest is missing or broken.
- 2026-11-24: Every admin change is one commit through the Git Data API: upload blobs (XMLHttpRequest, for progress), then a tree on top of main, a commit and a ref update with force false. If main moved in between, it starts again from the newest commit (up to 3 tries). The Git Data API is used for every file size (the Contents API is limited and needs the old file's sha), and a blob can be up to 100 MB. Deleting = a tree entry with sha null.
